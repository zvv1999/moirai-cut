# .mot 模板文件协议草案

日期：2026-10-15。状态：设计草案，尚未实现 `.mot` 读写器或工作台入口。当前工作台仍导入、导出模板 JSON。

## 目的

将现有设计保存为可交换的声明式模板文件，使工作台、人和 AI 使用同一份数据。文件保存视觉设计、组合关系、内容接口及相对动效，实际声音和内容事件驱动实例时间。扩展名暂用 `.mot`，项目内含义为 Moirai Template；这是自定义文件格式，不表示已有第三方软件兼容。该后缀已有 OpenSim motion 数据等用途，识别必须依据清单的格式身份和版本，不能仅凭后缀；发布前再确定最终文件关联。

不另写一套与现有 Rust 类型平行的模板模型。封装层只负责文档身份、依赖和兼容信息，设计字段沿用原生模型。

## 现有标准与先例

已完成 [官方资料调研](mot-format-standards-research-20261015.md)。MOGRT / Apple Motion 提供公开控件的产品先例，dotLottie 提供依赖封装先例，Rive RML / CLI 提供 AI 与编辑器共享模型及验证闭环的先例，Creatomate 提供声明式 JSON 创作先例。OTIO 适合编译后的时间线交换。

第一版优先实现原生设计的无损交换。Lottie、dotLottie、Rive 等可作为后续外部动效适配候选；采用 ZIP / JSON 不代表已与这些格式兼容，也不代表已有对应运行时。JSON Schema 只负责结构层，语义、能力和视觉结果分别验证。

## 已有基础与缺口

| 内容 | 当前实现 | `.mot` 需要补充 |
| --- | --- | --- |
| 可复用花字、字幕样式、图文动效 | `dynamic_asset::Definition`，`moirai.dynamic-asset.v1` | 样式文档的文件入口 |
| 模板组合、布局与编排 | `model::Template`，`moirai.template.v2` | 编排文档的文件入口与可复用性检查 |
| 结构、语义和执行能力校验 | Rust 校验器与 schema/capabilities | 文件入口复用同一套校验 |
| 图像、视频和音效 | 资源槽、绑定、资产目录与哈希 | 将机器本地资产 ID 映射为可携带依赖 |
| 版本 | schemaVersion 和本地 revision | 区分封装版本、设计版本、本地保存版本 |
| 实际成片 | 独立生产任务、工程、预览与评审 | 可选附预览；不把预览当模板定义或质量认证 |

源代码：`rust/crates/footage/src/templates/model.rs`、`dynamic_asset.rs`、`composition.rs`、`ontology.rs`、`api.rs`；现有 JSON 入口在 `apps/web/src/templates/workbench.tsx`。

## 文件结构

建议 `.mot` 使用 ZIP 容器。结构化内容使用 UTF-8 JSON，插画、动图、音效等依赖使用独立文件，避免仅换扩展名后仍依赖原机器的素材库。

```text
keyword-pop.mot
├── manifest.json         封装身份、入口、依赖与所需能力
├── definition.json       一个原生样式或编排文档
├── assets/               文件内依赖，可为空
├── fonts/                随文件提供的字体，可为空
└── preview/              可选封面与示例视频
```

第一版一个文件只含一个主文档。先完成单文件交换，再考虑批量模板库封装。AI 编辑解包后的 JSON；文件工具完成打包，不把二进制素材或视频塞入模型上下文。

以下是封装清单的字段草案，示例中的无素材依赖样式可使用空 `dependencies`：

```json
{
  "format": "moirai.mot",
  "formatVersion": 1,
  "packageId": "keyword-pop",
  "packageVersion": "1.0.0",
  "document": {
    "kind": "style",
    "schemaVersion": "moirai.dynamic-asset.v1",
    "path": "definition.json"
  },
  "dependencies": [],
  "requires": []
}
```

`requires` 由 Rust 从实际文档推导，再与运行时能力核对；示例空数组不代表任意样式没有能力要求。实际导出文件须填入文档及依赖的内容哈希，具体规范由 Rust 文件模型确定，不能以 JSON 键排列或 ZIP 时间戳决定设计身份。

## 两种文档类型

| document.kind | 原生数据 | 用途 |
| --- | --- | --- |
| `style` | `Definition` | 一个可复用的字幕样式、重点花字、图文装饰或动效组件 |
| `composition` | `Template` | 多元素组合、布局选择、字幕/视觉/混音策略及事件编排 |

不把两种类型强制转换。当前 `Template` 能保存场景专属事件 ID，不能因能保存就宣称它可跨内容复用。以可复用模板导出时，Rust 必须验证：规则只依赖可声明的输入和通用事件，不能仍依赖某次工程的 inputId、词下标、真实人脸坐标或场景事件 ID。无法无损表达时返回具体问题，不丢弃字段后继续导出。

当前 `Definition` 的使用说明属于指导信息，不自动等同于可执行约束。可执行规则继续使用已有的结构化字段和校验器。

## 设计与应用边界

文件应携带：

- 图层、分组、样式、默认资源、输入槽与内容绑定。
- 相对定位、文字尺寸关联、布局约束及已有可执行降级规则。
- 独立效果定义及作用目标；转场保留前后对象关系。
- 入场、保持、退场等相对运动，以及事件触发规则。
- 可编辑范围、默认文案和用途说明。

本次应用另行保存：真实文案/转写、选中的重点、实际素材、声音与画面事件、保护区、适配参数和观测结果。编译后的绝对时间、关键帧实例、轨道、生产进度不写回模板定义。

例如，一个花字样式可以定义“重点文字绑定 + 弹入效果 + 图标依附 + 边界约束”。换一段 TTS 后，文字、起止时间与实例位置重新求解；不修改样式。动效、滤镜和转场通过原有目标关系组合，能否作用于文字、图形或媒体由原生能力契约决定。

局部动画仍有关键帧和时长。需明确入场/保持/退场、可伸缩区、循环结束条件以及事件窗口过短时的处理；这些规则属于原生设计与执行契约，实际落在成片第几秒由 Application 和编译器决定。时间伸缩的保护区与画面避让的空间保护区分别表达。

## 公开参数与编辑能力

完整设计与使用者看到的公开控件分别表达。当前 `Definition.inputs` 提供文字输入基础；通用公开参数仍需在原生模型中补齐设计与实现，包括稳定 ID、类型、默认值、范围、单位、分组和属性绑定。封装清单不另建一套样式参数。

公开控件引用原生对象和属性；本次替换值由 Application 保存。修改模板源设计与调整某次应用必须保持明确边界。UI 和 AI 使用同一参数与验证接口。

外部动画的编辑能力需分别声明：完整源图层编辑、公开参数编辑、仅播放。即使某播放器能播放文件，也不能声称已转换为 Moirai 原生元素。适配器必须说明支持的格式/播放器版本、能力子集以及转换损失；未知必需效果不得静默忽略。

## 素材与字体依赖

依赖清单每项至少描述：包内唯一 ID、类别、原生引用、包内相对路径或明确的外部需求、内容哈希和缺失处理方式。

- 原生 `resourceBindings.assetId` 在导出时对应清单中的资源；导入时由 Rust 建立包内引用到新机器资产 ID 的映射。
- 内容相同的资产按哈希去重，不能依赖两个机器恰好使用相同 ID。
- 字体记录具体字体及可用时的字形文件身份。外部字体缺失时由声明的替代策略处理，并记录替代；不能宣称视觉完全一致。
- 包内依赖完整时可以离线导入。存在外部需求时，导入结果明确列出待补素材，不自动猜测本机路径或下载地址。
- 字号、画布区域、相对时间等沿用当前 schema 的单位；打包不做隐式坐标或时间单位转换。

可选预览绑定对应文档和依赖哈希。换文案、设计或资源后的预览不能沿用为新版本结果。评审记录如需交换，作为带作用域的附加证据处理，不用于跳过目标运行时的校验。

## 版本和导入语义

分别保留三种版本：

1. `formatVersion`：容器和清单如何解析。
2. 内层 `schemaVersion`：设计字段与执行语义如何解析。
3. `packageVersion`：同一模板发布了哪一版设计。原生 `revision` 是本地并发编辑版本，不作为跨机器覆盖凭据。

导入默认创建本地草稿，不覆盖同名模板。更新现有模板必须走已有的 revision/idempotency 协议。包版本和内容哈希保留为来源身份。

Rust 导入流程：读取清单 → 校验版本和包内路径 → 校验依赖哈希 → 解析原生文档 → 校验引用和能力 → 解析/导入依赖 → 生成本地草稿。过程中使用临时区，失败时不留下半导入的模板。迁移通过版本化转换进行，未知必需能力或字段报出明确错误，不能静默略过效果。

## 人与 AI 共用接口

工作台负责打开文件、显示可编辑控件和预览；Rust 负责协议解析、依赖解析、校验、迁移和导出；AI 使用同一 schema 和接口读写，不能另造私有字段或直接绕过校验改库。

建议向 UI/MCP 共用暴露四类操作：inspect（读文档与依赖）、validate（返回结构化问题）、import（创建本地草稿）、export（生成文件）。名称和路由在实现时确定，不代表现在已有这些接口。

AI 的生成闭环是读取 schema/能力 → 生成或修改原生 JSON → 校验 → 使用独立 Sample 试映 → 检查实际结果。文件合法只证明可读取和执行，不等于风格或视觉质量通过。

## 最小落地与验收

第一步实现 Rust 封装模型、读写和依赖解析；从 Rust 生成 JSON Schema。第二步接工作台 `.mot` 导入导出和相同的 MCP 能力。第三步使用真实花字与带插画的模板完成以下验证：

- 导出再导入，图层、样式、相对动效与关系不丢失。
- 在没有原数据库资产 ID 的环境解析依赖并生成成片。
- 同一文件换短词、长词、声音节奏后，实例时间变化，模板定义保持不变。
- 同 revision 的未保存草稿不能冒充已保存设计；应用专属事件依赖有明确处理。
- 缺素材、字体、未知能力和旧协议版本都返回可定位的问题。

本草案没有实现上述文件能力，也没有将现有库记录自动认证为可复用 `.mot` 模板；现有原生模型和 JSON 导入导出可以作为实现基础。
